05  |  AI 통합검색 구현

제약 조건과 기술 선택

AI를 온프레미스에서 구동하려면 고성능 GPU 서버가 필요하다. 하지만 이 인프라는 기능 개선 사업의 범위를 넘어섰다. 그래서 우리는 가진 것 위에서 작동하는 AI 검색을 선택했다.

① 검색층

가진 것을 지켰다

기존 Elasticsearch 검색 구조를 유지했다. Nori 형태소 분석, 유의어 사전, 4개 인덱스 동시 검색을 활용하고, Apache Tika와 PageIndex로 본문 추출 범위를 확장했다.

비용 추가 인프라 비용 없음

② 생성층

빌려 썼다

자체 GPU 서버 대신 OpenAI GPT-4o API를 사용했다. LLM은 답을 처음부터 만들어내는 것이 아니라, 사용자 질의 확장과 검색 결과 해석에 사용했다.

비용 호출량 기반 과금

③ 운영층

통제했다

API 키 노출과 비용 증가를 막기 위해 Drupal 서버를 경유하는 LLM Proxy 구조를 두었다. Rate Limit과 일일 예산 상한을 설정해 운영 비용을 통제했다.

비용 상한 $20/일

이것은 제약의 목록이 아니라 1단계 구성안이다. 기존 검색 구조 위에 최소한의 LLM 레이어를 얹어 작동하는 RAG를 만들었다. 다음 단계는 벡터 임베딩 기반 의미 검색이다. 확보된 AI 메타데이터와 문서 데이터를 벡터화하면, LLM 호출 없이도 의미 검색이 가능해진다.

모델을 소유하지 않아도, 검색 구조를 통제하면 AI 검색은 구현할 수 있다.
